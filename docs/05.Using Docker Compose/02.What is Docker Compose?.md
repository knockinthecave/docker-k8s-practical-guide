# 도커 컴포즈가 뭘까

## 1. 개념

- 도커 컴포즈는 `docker build`와 `docker run`을 **대체**할 수 있다.
- 다수의 `docker build` / `docker run`을 **하나의 구성 파일**로 관리한다.
- 모든 서비스(컨테이너)를 한 번에 시작하고, 필요하면 이미지도 빌드하는 **오케스트레이션 명령 셋**이다.
- 하나의 명령으로 전체를 시작하고, 하나의 명령으로 전체를 중지/삭제할 수 있다.
- 단일 컨테이너 앱에도 쓸 수 있지만, **다중 컨테이너**일 때 장점이 크다.

### 하지 않는 것

- `Dockerfile`을 대체하지 않는다. (이미지를 만드는 레시피는 여전히 Dockerfile)
- 이미지나 컨테이너 자체를 대체하지 않는다. 더 쉽게 시작하게 해줄 뿐이다.
- **여러 호스트에 걸친 컨테이너 관리에는 적합하지 않다.** 하나의 동일한 호스트에서 다중 컨테이너를 관리하는 데 강점이 있다. (여러 호스트는 Kubernetes 영역)
- 개발 환경 외(테스트, 단일 서버 배포 등)에서도 활용도가 높다.

## 2. 핵심은 "서비스"

- `service` = 실제 컨테이너 하나를 정의한 것이다.
- 서비스 안에서 정의할 수 있는 것: 이미지/빌드, 게시할 포트, 환경 변수, 볼륨, 네트워크, 시작 순서 등
- 결국 터미널에서 치던 `docker run -p ... -e ... -v ...` 옵션들을 **파일로 옮겨 적은 것**이다.

| `docker run` 옵션 | compose 키 |
|-------------------|-----------|
| 이미지 이름 | `image:` |
| `docker build` | `build:` |
| `-p 8000:8000` | `ports:` |
| `-e KEY=value` | `environment:` |
| `--env-file` | `env_file:` |
| `-v 이름:/경로` | `volumes:` |
| `--network` | `networks:` (생략 가능) |

## 3. 파일 작성법

- 파일명은 `docker-compose.yml` (또는 `compose.yaml`).
- **`version:` 키는 이제 쓰지 않는다.**
  - 현재 Compose(v2 이상, 실습 환경은 v5.6.0)에서는 `version`이 **obsolete(무시되는 속성)** 이다. 써도 동작에는 영향이 없고 경고만 나온다.
  - 파일 포맷은 Compose Specification을 따르며 버전 구분이 없다.
- 최상위 키는 `services:`, `volumes:`, `networks:` 등이다.
- **들여쓰기가 가장 중요하다.** YAML은 들여쓰기로 종속 관계를 표현한다. (스페이스 2칸, 탭 불가)
- `services:` 아래의 **각 하위 키가 컨테이너 하나**이다. 하위 요소가 최소 1개는 있어야 한다.
- 그 키 이름(`backend`, `frontend`, `postgresdb`)이 **서비스명**이고, 네트워크 안에서의 **호스트명**이 된다.
- 각 서비스 아래에서 다시 들여쓰기하여 컨테이너의 속성을 적는다.

## 4. 실습 `docker-compose.yml` 해설

```yaml
services:
  postgresdb:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: todo
      POSTGRES_PASSWORD: todo
      POSTGRES_DB: todo
    ports:
      - "5432:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U todo -d todo"]
      interval: 3s
      timeout: 3s
      retries: 10

  backend:
    build: ./backend
    environment:
      DATABASE_URL: postgresql://todo:todo@postgresdb:5432/todo
    ports:
      - "8000:8000"
    depends_on:
      postgresdb:
        condition: service_healthy

  frontend:
    build: ./frontend
    ports:
      - "3000:80"
    depends_on:
      - backend

volumes:
  pgdata:
```

전체 구조: `frontend(3000) → /api 프록시 → backend(8000) → postgresdb(5432)`

### 4-1. `image` vs `build`

- `image: postgres:16-alpine`: 이미 있는 이미지를 그대로 사용한다. (`docker run postgres:16-alpine`)
- `build: ./backend`: 해당 경로의 `Dockerfile`로 이미지를 빌드해서 사용한다. (`docker build ./backend`)
- compose로 띄운 컨테이너는 `up -d`로 백그라운드 실행하며, `--rm` 같은 제거 옵션도 따로 줄 필요가 없다. 정리는 `docker compose down`이 한다.

### 4-2. `environment`

- 환경 변수를 지정한다. (`docker run -e`)
- 키-값 쌍은 `-` 없이 **콜론**으로 쓴다: `POSTGRES_USER: todo`
- 리스트 형태(`- POSTGRES_USER=todo`)도 가능하지만 한 파일에서는 하나로 통일한다.
- **환경 변수 파일**도 지정할 수 있다.

```yaml
    env_file:
      - ./env/postgres.env
```

- 실습에서는 값을 파일에 직접 적었지만, 실제 환경에서는 `.env` / 시크릿으로 분리하고 커밋하지 않는다.

### 4-3. `ports`

- `"호스트포트:컨테이너포트"` 형식이다. (`docker run -p`)
- `backend`의 `8000:8000`, `frontend`의 `3000:80`은 브라우저에서 접근하기 위해 연 것이다.
- `postgresdb`에 `5432:5432`를 연 이유는 **호스트(내 Mac)의 DBeaver/IntelliJ 등에서 `jdbc:postgresql://localhost:5432/todo`로 접속**하기 위해서다.
- 포트를 열지 않아도 같은 네트워크 안의 `backend`는 `postgresdb:5432`로 접속할 수 있다. 즉 `ports`는 **호스트에서 접근할 때만** 필요하다.
- 실제 배포에서는 DB 포트를 열지 않는 것이 일반적이다. 로컬에서만 쓰려면 `"127.0.0.1:5432:5432"`로 바인딩한다.

### 4-4. `volumes` (서비스 안)

```yaml
    volumes:
      - pgdata:/var/lib/postgresql/data
```

- `볼륨이름:컨테이너 내부 경로` → **명명된 볼륨**을 컨테이너 경로에 연결한다.
- 컨테이너를 삭제해도 DB 데이터는 `pgdata` 볼륨에 남는다.

### 4-5. 최상위 `volumes`

```yaml
volumes:
  pgdata:
```

- 서비스에서 사용하는 **명명된 볼륨은 최상위 `volumes:`에 반드시 나열**해야 한다. 도커가 명명된 볼륨을 인식하기 위해서다.
- 콜론만 쓰면 기본 설정으로 생성된다. (`pgdata:`)
- **다른 서비스가 같은 볼륨 이름을 쓰면 그 볼륨이 공유된다.** 여러 컨테이너가 같은 볼륨(같은 폴더)을 사용할 수 있다.
- **익명 볼륨과 바인드 마운트는 선언할 필요가 없다.**

### 4-6. 네트워크 (`networks`를 쓰지 않은 이유)

- `networks:`로 네트워크를 선언할 수 있지만, 이 실습에서는 **쓰지 않았다.**
- Compose는 파일에 정의된 모든 서비스에 대해 **새 기본 네트워크를 자동 생성**하고, 모든 서비스를 그 네트워크에 넣는다.
- 그래서 같은 파일의 서비스들은 별도 설정 없이 **서비스명을 호스트명처럼** 써서 통신할 수 있다.
  - `DATABASE_URL: postgresql://todo:todo@postgresdb:5432/todo`의 `postgresdb`가 그것이다.
- 컨테이너 안에서 `localhost`는 **자기 자신**을 가리킨다. 다른 컨테이너를 부를 땐 서비스명을 쓴다.
- 직접 만든 네트워크를 쓰고 싶다면 `networks:`로 선언해서 관리해도 된다. (기본 네트워크 대신 사용, 서비스별로 분리 가능)

### 4-7. `healthcheck`

```yaml
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U todo -d todo"]
      interval: 3s
      timeout: 3s
      retries: 10
```

- 컨테이너가 **떠 있는 것(started)** 과 DB가 **준비된 것(healthy)** 은 다르다. 이를 구분하기 위한 검사다.
- `test`: 이 명령이 성공(exit 0)하면 healthy. `pg_isready`는 Postgres 접속 가능 여부를 확인한다.
- `interval`: 검사 주기 / `timeout`: 1회 검사 제한 시간 / `retries`: 연속 실패를 허용할 횟수

### 4-8. `depends_on`

```yaml
  backend:
    depends_on:
      postgresdb:
        condition: service_healthy   # postgresdb 가 healthy 일 때까지 대기

  frontend:
    depends_on:
      - backend                      # backend 컨테이너가 시작된 뒤
```

- **시작 순서**를 제어한다. 종료 시에는 역순이다.
- 리스트 형태(`- backend`)는 "컨테이너가 시작됐는지"만 본다.
- `condition: service_healthy`는 `healthcheck`가 통과할 때까지 기다린다. DB가 준비되기 전에 backend가 접속을 시도해서 죽는 문제를 막는다.

## 5. 자주 쓰는 명령

```bash
docker compose up                 # 생성 + 시작 (포그라운드)
docker compose up -d              # 백그라운드로 시작
docker compose up --build         # 이미지를 다시 빌드하고 시작
docker compose build --no-cache   # 캐시 없이 이미지 빌드
docker compose down               # 컨테이너 + 네트워크 삭제 (볼륨은 유지)
docker compose down -v            # 볼륨까지 삭제 (DB 데이터 삭제)
docker compose logs -f backend    # 특정 서비스 로그
docker compose ps                 # 상태 확인
docker compose config             # 파일 문법/최종 설정 검증
```

- 컨테이너 이름은 `<프로젝트명>-<서비스명>-<번호>` 형식으로 자동 생성된다. (프로젝트명 기본값 = 폴더명, 번호는 scale 시 인스턴스 번호)
- 설정을 바꾼 뒤 `up -d`만 다시 실행하면 **변경된 서비스만** 재생성된다.

### 실행과 정리

- `docker compose up`: 모든 서비스를 시작한다. 필요한 이미지는 **가져오고(pull), 없으면 빌드**한다. 서비스별 로그가 한 터미널에 섞여 **출력이 상당히 많다.**
- `docker compose up -d`: detached(백그라운드) 모드로 실행한다.
- `docker compose down`: 컨테이너를 삭제하고 **기본 네트워크도 제거**한다. 단, **볼륨은 삭제되지 않는다.**
- `docker compose down -v`: 볼륨까지 함께 제거한다.
- 이미지/컨테이너 정리는 compose 명령이 아니라 도커 명령으로 한다.
  - `docker image prune -a`: 컨테이너가 쓰지 않는 **모든 이미지** 제거
  - `docker container prune`: **정지된 컨테이너** 정리

## 6. `build` 상세

- compose를 쓰면 `docker build`를 직접 실행하는 단계가 없어진다. `up` 할 때 이미지가 없으면 compose가 알아서 빌드한다. 대신 **빌드에 필요한 정보**를 파일에 적어준다.

```yaml
  backend:
    build: ./backend            # 간단 형태
```

- `build: ./backend`: `Dockerfile`이 있는 폴더를 알려준다. compose가 거기서 `Dockerfile`을 찾아 빌드하고, **빌드된 이미지를 그 컨테이너가 사용**한다.
- 이 경로는 **빌드 컨텍스트**(= 이미지를 만들 때 도커로 보내지는 파일 범위)이기도 하다. 즉 `./backend` 안의 파일만 `COPY` 대상이 된다.

### 긴 형태

```yaml
  backend:
    build:
      context: ./backend        # 빌드 컨텍스트 (Dockerfile 이 있는 곳)
      dockerfile: Dockerfile    # 파일 이름이 다를 때 지정 (예: Dockerfile.dev)
      args:                     # 빌드 시 인수 (Dockerfile 의 ARG)
        NODE_VERSION: 20
```

| 키 | 설명 |
|----|------|
| `context` | 빌드 컨텍스트 경로. 상대 경로는 compose 파일 기준이다. `../shared` 처럼 **바깥 폴더**도 지정할 수 있다. |
| `dockerfile` | 컨텍스트 안의 Dockerfile 이름. 기본값은 `Dockerfile`이라 **이름이 다를 때만** 쓴다. |
| `args` | 빌드 시 인수. **Dockerfile에 `ARG`가 선언되어 있어야** 의미가 있다. 런타임 `environment`와는 다르다. |

- 컨텍스트를 바깥 폴더로 잡으면 그 안의 파일을 `COPY`로 쓸 수 있다. 반대로 컨텍스트 **밖의 파일은 `COPY`할 수 없다.**
- 컨텍스트가 크면 빌드가 느려지므로 `.dockerignore`로 제외한다. (이 실습의 `frontend/.dockerignore` 참고)

## 7. `ports`, 바인드 마운트, 익명 볼륨

### `ports`

```yaml
    ports:
      - "80:80"      # 호스트 포트:컨테이너(내부) 포트
```

- 게시할 포트를 지정한다. 따옴표로 감싸는 것을 권장한다. (`22:22` 같은 값은 YAML이 숫자로 잘못 해석할 수 있다.)

### 바인드 마운트

```yaml
    volumes:
      - ./backend:/app
```

- `./backend`의 **모든 내용을 컨테이너의 `/app`과 공유**한다. 호스트에서 코드를 고치면 컨테이너에 바로 반영된다. (개발용)
- `docker run -v`와 달리 **상대 경로(`./`)를 쓸 수 있다.**
- 바인드 마운트이므로 **최상위 `volumes:`에 선언하지 않는다.**

### 익명 볼륨

```yaml
    volumes:
      - ./backend:/app
      - /app/node_modules    # 이름 없이 컨테이너 경로만 적는다
```

- 이름 없이 경로만 쓰면 익명 볼륨이다. 역시 **최상위 `volumes:`에 선언할 필요가 없다.**
- 위 예처럼 바인드 마운트(`./backend`)가 컨테이너 안의 `/app/node_modules`를 **덮어쓰지 않도록 보호**하는 용도로 쓴다. 더 구체적인 경로가 우선하기 때문이다.
- 이 실습의 `docker-compose.yml`에는 사용하지 않았다. (개념 예시)

| 종류 | 서비스 안 표기 | 최상위 `volumes:` 선언 |
|------|----------------|------------------------|
| 명명된 볼륨 | `pgdata:/var/lib/postgresql/data` | **필요** |
| 바인드 마운트 | `./backend:/app` | 불필요 |
| 익명 볼륨 | `/app/node_modules` | 불필요 |

## 8. `depends_on`과 서비스 간 통신 보충

- `depends_on`은 **도커 컴포즈에만 있는 옵션**이다. 도커(`docker run`)는 컨테이너를 하나씩 개별 실행하므로 필요 없다.
- compose는 여러 컨테이너를 동시에 만들기 때문에 **이미 실행 중이어야 하는 다른 컨테이너에 의존**하는 경우가 생긴다.
  - 예: `backend`는 `postgresdb`에 의존한다. 먼저 `postgresdb`를 띄운 뒤 `backend`를 만들어야 한다.
- 값에는 **의존하는 서비스의 이름**(`services:` 아래의 키)을 적는다.

```yaml
    depends_on:
      - postgresdb
```

- 리스트 형태는 **시작 순서만** 보장한다. DB가 접속 가능한 상태인지까지 기다리려면 `condition: service_healthy`와 `healthcheck`를 쓴다. (4-7, 4-8 참고)
- 실제 컨테이너 이름은 `<프로젝트명>-postgresdb-1`처럼 더 길게 만들어지지만, **`services:` 아래의 이름(`postgresdb`)이 네트워크 안에서 호스트명(DNS)으로 동작**한다.
- 따라서 `backend`와 `postgresdb`는 서로 **`services`에 적은 이름**으로 통신한다. 코드/접속 문자열에 긴 컨테이너 이름이 아니라 서비스명을 쓴다.

## 9. 재빌드 동작

- `docker compose up`을 할 때마다 이미지를 **항상 다시 빌드하지는 않는다.**
  - 이미지가 **아직 없을 때**만 자동으로 빌드한다.
  - 이미 이미지가 있으면 **소스 코드가 바뀌었더라도 기존 이미지를 그대로 재사용**한다. (코드 변경을 자동 감지해서 리빌드하지는 않는다.)
- 코드나 Dockerfile을 바꿨다면 **직접 리빌드를 지시**한다.

```bash
docker compose up --build         # 빌드를 다시 수행하고 시작
docker compose build              # 빌드만
docker compose build --no-cache   # 레이어 캐시까지 무시하고 처음부터
```

- `--build`를 줘도 Dockerfile의 **변경되지 않은 레이어는 캐시를 재사용**하므로, 바뀐 부분부터만 다시 빌드된다. 그래서 빠르다.
- 반대로 `docker-compose.yml`의 설정(포트, 환경 변수 등)을 바꾸고 `up -d`만 하면 **설정이 바뀐 서비스만 컨테이너가 재생성**된다. 이미지 빌드는 별개다.
- 코드를 자주 고치는 개발 중에는 바인드 마운트(7장)나 `docker compose watch`를 쓰면 매번 리빌드하지 않아도 된다.

## 10. 인터랙티브 모드 (`stdin_open`, `tty`)

`docker run -it`의 `-i`, `-t`에 해당하는 옵션이다.

```yaml
  backend:
    stdin_open: true   # -i : 표준 입력(stdin)을 열어 둔다
    tty: true          # -t : 가상 터미널(TTY)을 연결한다
```

| 옵션 | docker run | 의미 |
|------|-----------|------|
| `stdin_open: true` | `-i` | 컨테이너가 **입력을 받을 수 있게** 입력 채널을 열어 둔다. |
| `tty: true` | `-t` | 터미널에 연결할 수 있게 **가상 터미널**을 붙인다. |

- 두 옵션을 함께 쓰면 **인터랙티브 모드**가 된다. (프롬프트 입력을 받는 프로그램, 쉘 등)
- `up -d`(detached) 로 띄워도 컨테이너 내부적으로는 입력을 받을 수 있는 상태가 유지된다. 필요할 때 나중에 붙을 수 있다.

```bash
docker attach <컨테이너 이름>                # 실행 중인 컨테이너의 입출력에 연결
docker compose exec backend sh              # 실행 중인 서비스 안에서 쉘 열기
docker compose run --rm backend sh          # 일회용 컨테이너로 쉘 열기
```

## 11. 의존성 정리: frontend → backend → postgresdb

```yaml
  frontend:
    depends_on:
      - backend                  # backend 컨테이너가 시작된 뒤 frontend 시작
  backend:
    depends_on:
      postgresdb:
        condition: service_healthy   # DB 가 healthy 가 된 뒤 backend 시작
```

- 시작 순서: `postgresdb` (healthy) → `backend` → `frontend`
- 종료 순서는 그 반대(`frontend` → `backend` → `postgresdb`)이다.
