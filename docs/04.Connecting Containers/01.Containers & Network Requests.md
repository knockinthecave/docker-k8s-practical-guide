# 컨테이너와 네트워크 요청

> 다중 컨테이너 구조에서는 컨테이너 간 통신이 필요하다. 컨테이너 안의 앱이 **외부 API**, **호스트 머신의 서비스**, **다른 컨테이너**와 통신하는 세 가지 경우를 우리 FastAPI 앱 실습과 함께 정리한다.

## 통신의 세 가지 유형

| # | 통신 대상 | 설정 | 주소 | 실습 엔드포인트 |
|---|-----------|------|------|-----------------|
| 1 | 외부 API / 웹 (WWW) | **필요 없음** | 평소 쓰던 URL | `/films`, `/people` |
| 2 | 호스트 머신의 서비스 | 특수 도메인 사용 | `host.docker.internal` | `/visits` (호스트의 Redis) |
| 3 | 다른 컨테이너 | 도커 **네트워크** | 컨테이너 이름 (`cache`) | `/visits` (cache 컨테이너) |

FastAPI 서버는 컨테이너 안에서 도는 코드지만, 외부 API나 호스트 머신의 DB, 다른 컨테이너와도 통신할 수 있다.

## 1. 컨테이너 → 외부 API (WWW)

기본적으로 컨테이너는 웹에 요청을 보낼 수 있다. 도커화된 앱 내부에서 웹 API나 웹 페이지와 통신하는 데에는 **설정 변경이 필요 없다.**

- 실습 앱은 `swapi.dev`(스타워즈 데이터 API)에 HTTP GET 요청을 보낸다.
  - `swapi.dev/api/films`: 영화 정보
  - `swapi.dev/api/people`: 등장인물 정보
- `main.py`의 `fetch_swapi()`가 이 요청을 보내고, `/films`·`/people`이 결과를 돌려준다.
- 외부 주소는 `SWAPI_URL` 환경변수로 바꿀 수 있다. ([06.ARGuments & ENVironment Variables](../03.Managing%20Data%20in%20Images%20%26%20Containers/06.ARGuments%20%26%20ENVironment%20Variables.md) 참고)

```bash
docker run -d -p 8000:8000 --name app docker-practice-image
curl localhost:8000/films
```

- 요청에 실패하면(타임아웃, 인증서 오류 등) 앱은 `502`와 사유를 돌려준다. `swapi.dev`는 가끔 응답이 느리거나 실패하므로 이때는 정상 동작이다.

## 2. 컨테이너 → 호스트 머신의 서비스

호스트 머신에서 실행 중인 서비스(예: 로컬 DB)로 요청하면 어떻게 될까?

**주소에 `localhost`를 쓰면 실패한다.** 컨테이너 안의 `localhost`는 호스트가 아니라 **컨테이너 자기 자신**이기 때문이다.

- 코드에서 도커에게 힌트를 주는 **특수 도메인**으로 바꿔야 한다: `host.docker.internal`
- 도커가 이 도메인을 **호스트 머신의 IP 주소로 변환**해 준다. 우리가 IP를 찾을 필요가 없다.
- 통신 자체는 되지만, 반드시 이 도메인을 써야 한다. 이것이 도커화된 앱 통신의 두 번째 유형이다.

실습: 앱의 `REDIS_HOST`를 바꿔 보면 차이가 보인다.

```bash
# localhost 그대로 (기본값) → 컨테이너 자신에게 접속하므로 실패
docker run -d -p 8000:8000 --name app docker-practice-image
curl -X POST localhost:8000/visits    # 503: redis unavailable (localhost:6379)

# 호스트에서 6379로 열려 있는 Redis에 접속
docker rm -f app
docker run -d -p 8000:8000 --name app -e REDIS_HOST=host.docker.internal docker-practice-image
curl -X POST localhost:8000/visits    # {"visits":1}
```

- 앱 코드를 고치지 않고 **환경변수만 바꿔서** 접속 대상을 바꿨다. 이것이 ENV로 주소를 뺀 이유다.
- 호스트에서 쓰던 Redis의 `visits` 키가 바뀌므로, 같은 키를 다른 작업에서 쓰는지 확인하고 실행한다.
- `host.docker.internal`은 **Docker Desktop(Mac/Windows)** 에서 기본 제공된다. 리눅스에서는 `--add-host=host.docker.internal:host-gateway` 옵션을 붙여야 한다.

## 3. 컨테이너 → 컨테이너

예를 들어 Redis 공식 이미지를 `cache`라는 이름의 컨테이너로 띄우고, 앱 컨테이너가 여기에 접속한다고 하자.

### 방법 1: IP 주소 직접 사용 (불편함)

```bash
docker container inspect cache    # NetworkSettings의 IPAddress 값을 확인
```

- 이 IP를 `REDIS_HOST`에 넣으면 통신은 된다.
- 하지만 매번 주소를 찾아야 하고, 컨테이너를 다시 만들어 **IP가 바뀌면** 일일이 고쳐서 하드코딩해야 한다.
- 컨테이너는 기본적으로 **분리와 격리**가 원칙이다. 이것이 도커를 쓰는 핵심 이유이기도 하다. 그래서 통신하려면 환경을 별도로 만들어 줘야 한다.

### 방법 2: 도커 네트워크 (권장)

도커로 **컨테이너 네트워크**를 만들고, `--network` 옵션으로 컨테이너들을 같은 네트워크에 넣는다.

```bash
docker network create app-net
```

- 볼륨과 달리 네트워크는 도커가 알아서 만들어 주지 않는다. **직접 `docker network create`로 만들어야 한다.** (그래서 `--network app-net`만 쓰면 "network not found"로 실패한다)
- 복잡한 설정 없이 **이름만 붙이면** 된다. 나머지는 도커가 처리한다.
- 같은 네트워크 안의 컨테이너는 서로 통신할 수 있다. **컨테이너 이름이 곧 주소(호스트명)** 가 된다.
  - 주소를 `cache:6379`처럼 쓰면 된다.
  - 직접 만든 네트워크에서만 이 이름 해석이 동작한다.

```bash
# Redis 컨테이너 (-p 없음)
docker run -d --name cache --network app-net \
  -v redis-data:/data \
  redis:alpine redis-server --appendonly yes

# 앱 컨테이너
docker run -d --name app --network app-net -p 8000:8000 \
  -e REDIS_HOST=cache docker-practice-image

curl -X POST localhost:8000/visits    # {"visits":1}
curl -X POST localhost:8000/visits    # {"visits":2}
```

- 앱 코드는 `REDIS_HOST`가 `cache`든 `host.docker.internal`이든 똑같이 동작한다. **주소만 환경변수로 바꾼다.**

### 영속성 확인

Redis 컨테이너를 지웠다 다시 만들어도 볼륨 덕분에 값이 이어진다. ([03.Understanding Volumes](../03.Managing%20Data%20in%20Images%20%26%20Containers/03.Understanding%20Volumes.md) 참고)

```bash
docker rm -f cache
docker run -d --name cache --network app-net -v redis-data:/data \
  redis:alpine redis-server --appendonly yes
curl localhost:8000/visits            # {"visits":2}
```

- `--appendonly yes`가 있어야 데이터가 디스크에 기록되어 재시작 후에도 남는다.

## `-p`는 언제 필요한가

`-p`(포트 게시)는 **호스트 머신이나 컨테이너 네트워크 바깥에서 접속**할 때만 필요하다.

| 컨테이너 | `-p` | 이유 |
|----------|------|------|
| `app` | 필요 (`-p 8000:8000`) | 호스트의 `curl`/브라우저가 접속한다 |
| `cache` | **불필요** | 같은 네트워크의 `app`만 접속한다 |

- 컨테이너끼리만 통신한다면 포트를 게시할 필요가 없다. 네트워크 안에서는 자유롭게 통신한다.
- 게시하지 않으면 외부에 노출되지 않으므로 DB 같은 컨테이너는 보안상 게시하지 않는 편이 좋다.

## 정리

- 컨테이너 → **외부 API**: 설정 없이 가능하다.
- 컨테이너 → **호스트**: `localhost` 대신 `host.docker.internal`을 쓴다.
- 컨테이너 → **컨테이너**: `docker network create`로 네트워크를 만들고 `--network`로 묶은 뒤, **컨테이너 이름**으로 접속한다.
- 접속 주소는 코드에 박지 않고 **환경변수**(`REDIS_HOST`)로 받는다. 실행 환경이 바뀌어도 코드를 고칠 필요가 없다.
- 격리가 기본이고, 네트워크는 그 위에 통신 환경을 얹는 것이다. 다중 컨테이너 환경의 일반적인 시나리오다.
