# 이미지 확보하기: Docker Hub 이미지 vs 커스텀 이미지

> 컨테이너를 실행하려면 **이미지**가 필요하다. 이미지를 얻는 방법은 크게 두 가지다.
> 1. **Docker Hub에 이미 있는 이미지**를 가져다 실행한다.
> 2. **Dockerfile로 나만의 이미지**를 직접 빌드한다.

| 구분 | Docker Hub 이미지 실행 | 커스텀 이미지 빌드 |
|------|------------------------|--------------------|
| 이미지 출처 | 이미 만들어진 공개 이미지 | 내가 `Dockerfile`로 직접 빌드 |
| 필요한 것 | 이미지 이름 | `Dockerfile` + 내 애플리케이션 코드 |
| 주 용도 | Node, Redis, MySQL 같은 도구·서비스 | 내가 만든 애플리케이션 |
| 대표 명령 | `docker run <이미지>` | `docker build` → `docker run` |

---

## 1. Docker Hub의 이미지 실행하기

[Docker Hub](https://hub.docker.com)에는 공개된 이미지가 모여 있다. 이미지 이름만 알면 바로 컨테이너로 실행할 수 있다.

### 이미지를 찾는 순서

```
docker run <이미지>
      │
      ▼
로컬에 이미지가 있는가? ── 있음 ──▶ 바로 사용
      │
     없음
      ▼
Docker Hub에서 검색 ──▶ 이미지 다운로드 ──▶ 컨테이너 실행
```

- 도커는 **로컬을 먼저** 찾고, 없을 때만 Docker Hub에서 내려받는다.
- 이미지를 받은 뒤에는 그 이미지로 **컨테이너를 실행**한다.

### 예제: Node 컨테이너 실행

```bash
docker run -it node
```

- 인터랙티브 Node 터미널이 열려서 컨테이너 안의 Node를 직접 조작할 수 있다.
- `-it` 플래그를 붙여야 컨테이너와 **상호작용**할 수 있다.

| 플래그 | 의미 |
|--------|------|
| `-i` | 표준 입력을 열어 둔다 (입력 가능) |
| `-t` | 터미널(TTY)을 연결한다 |

### 컨테이너를 쓰는 이유

- 컨테이너 안의 Node는 **내 컴퓨터의 Node와 별개의 환경**이다.
- 그래서 로컬에 Node를 **설치하지 않아도** 쓸 수 있다.
- 컨테이너는 주변 환경과 **격리**되어 있다. 컨테이너 안에서 셸을 실행해도 그 셸이 내 시스템에 노출되지는 않는다.

> 이것이 컨테이너를 실행하는 가장 큰 의의다.

## 2. 커스텀 이미지 빌드하기

Docker Hub에 없는 **내 애플리케이션**은 직접 이미지로 만들어야 한다. 어떤 언어로 만든 애플리케이션이든 이미지로 빌드할 수 있다.

- 프로젝트 **루트 디렉토리**에 `Dockerfile`을 작성한다.
- `Dockerfile`에는 이미지를 빌드할 때 **실행할 명령**과 **도커에 대한 지시**가 들어간다.
- 명령어(instruction)는 관례상 **모두 대문자**로 쓴다.

### 예제: FastAPI 애플리케이션

이 레포의 `Dockerfile`이다.

```dockerfile
FROM python:3.14.5-alpine

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY main.py .

EXPOSE 8000

CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

### 명령어별 역할

| 명령어 | 역할 |
|--------|------|
| `FROM` | **베이스 이미지**를 지정한다. 항상 `FROM`으로 시작한다. |
| `WORKDIR` | 작업 디렉토리를 지정한다. 이후 모든 명령이 이 폴더에서 실행된다. |
| `COPY` | 로컬 파일을 이미지 안으로 복사한다. |
| `RUN` | **이미지를 빌드할 때** 명령을 실행한다. (예: 라이브러리 설치) |
| `EXPOSE` | 컨테이너가 사용하는 포트를 문서화한다. |
| `CMD` | **컨테이너를 시작할 때** 실행할 명령을 지정한다. |

#### FROM — 베이스 이미지

- 다른 이미지 위에 내 이미지를 쌓을 수 있다.
- 코드를 실행하는 데 필요한 **도구와 운영체제 레이어**가 베이스 이미지에 들어 있다.

#### COPY — 파일 복사

```dockerfile
COPY <로컬 경로> <이미지 내부 경로>
```

- 첫 번째 경로는 **가져올 로컬 경로**, 두 번째 경로는 **이미지 내부 경로**다.
- 컨테이너 안에는 로컬 머신과 **분리된 자체 파일 시스템**이 있다. 그래서 어떤 파일을 이미지에 넣을지 도커에게 알려줘야 한다.

#### WORKDIR — 작업 디렉토리

- 이후의 `COPY`, `RUN`, `CMD`가 실행되는 기준 폴더를 정한다.
- 루트(`/`)에 파일을 풀어 두기보다 `/app` 같은 **서브 폴더**를 쓰는 편이 좋다.
- 상대 경로보다 **절대 경로**가 무엇을 가리키는지 파악하기 쉽다.

#### RUN — 빌드 시점 명령

- 이미지의 작업 디렉토리에서 실행되며, 필요한 **라이브러리를 설치**할 때 쓴다.
- 파이썬은 `pip install -r requirements.txt`로 의존성을 설치한다.

#### CMD — 컨테이너 시작 명령

- 컨테이너가 시작될 때 실행할 명령이다. 서버를 띄우는 명령은 `RUN`이 아니라 **`CMD`** 에 쓴다.
- 명령은 `["uvicorn", "main:app"]`처럼 **배열**로 전달한다.

**RUN과 CMD의 차이**

| 구분 | RUN | CMD |
|------|-----|-----|
| 실행 시점 | 이미지를 **빌드**할 때 | 컨테이너를 **시작**할 때 |
| 용도 | 의존성 설치 등 준비 작업 | 서버 실행 등 컨테이너의 주 프로세스 |

> 이미지는 컨테이너의 템플릿이다. 의존성은 **빌드할 때 모두 설치**해 두고, 컨테이너가 **시작될 때** 서버를 띄운다고 생각하면 된다.

#### EXPOSE — 포트

- 웹 서버는 특정 포트(예: 80, 8000)를 열어 둬야 한다.
- 컨테이너는 **자체 내부 네트워크**를 쓰기 때문에, 그 포트는 기본적으로 로컬 머신에 노출되지 않는다. 컨테이너 안에서만 대기하므로 밖에서는 접근할 수 없다.
- `EXPOSE`는 사용하는 포트를 **선언(문서화)** 한다.
- 실제로 로컬에서 접근하려면 `docker run`에 `-p`로 포트를 연결해야 한다.

```bash
docker run -p 3000:80 <이미지>
#              로컬:컨테이너
```

- `-p`는 **publish**의 약자다. 접근하려는 **로컬 포트**를 컨테이너 포트와 연결해 준다.
- 값은 **콜론(`:`)을 기준으로 앞뒤 의미가 다르다.**

| 위치 | 예시 값 | 의미 |
|------|---------|------|
| 콜론 **앞** | `3000` | **로컬 머신(호스트)의 포트**. 브라우저에서 `localhost:3000`으로 접속한다. |
| 콜론 **뒤** | `80` | **컨테이너 내부의 포트**. 컨테이너 안의 애플리케이션이 실제로 대기하는 포트다. |

```
브라우저 ──▶ localhost:3000 ──(포트 연결)──▶ 컨테이너:80 ──▶ 앱
             (로컬 포트)                      (컨테이너 포트)
```

- 위 예시는 "로컬의 3000번 포트로 들어온 요청을 컨테이너의 80번 포트로 전달한다"는 뜻이다.
- 컨테이너 포트(뒤)는 애플리케이션이 사용하는 포트와 **반드시 일치**해야 한다. 이 레포의 FastAPI는 8000번에서 대기하므로 `-p 8000:8000`처럼 쓴다.
- 로컬 포트(앞)는 **비어 있는 포트라면 마음대로** 정할 수 있다. 예를 들어 `-p 3000:8000`이면 `localhost:3000`으로 접속한다.
- `EXPOSE`만 있고 `-p`가 없으면 포트는 **실제로 열리지 않는다.** `EXPOSE`는 문서화 목적일 뿐 동작에는 영향이 없다.

### 이미지 빌드하고 컨테이너 실행하기

`Dockerfile`을 작성했다면 도커에게 이를 기반으로 **새 커스텀 이미지를 빌드**하라고 지시한다.

```bash
# 1. 빌드: Dockerfile이 있는 경로를 알려준다 (현재 폴더라면 .)
docker build .

# 2. 실행: 빌드 결과로 나온 이미지 ID로 컨테이너를 실행한다
docker run -p 8000:8000 <이미지 ID>

# 3. 모니터링: 컨테이너 목록 확인 (-a는 종료된 컨테이너까지 표시)
docker ps -a

# 4. 중단: 실행 중인 컨테이너를 멈춘다
docker stop <컨테이너 이름 또는 ID>
```

| 명령 | 역할 |
|------|------|
| `docker build <경로>` | 해당 경로의 `Dockerfile`을 기반으로 이미지를 빌드한다. |
| `docker run <이미지 ID>` | 이미지 ID로 컨테이너를 실행한다. |
| `docker ps -a` | 컨테이너 상태를 확인한다. |
| `docker stop <컨테이너>` | 실행 중인 컨테이너를 중단한다. |

---

## 정리

- 이미지는 컨테이너에 필요한 **모든 코드, 로직, 설정**을 담고 있다.
- `docker run`으로 이미지의 **인스턴스**를 만들면 그것이 컨테이너다.
- 이미지는 **Docker Hub에서 가져오거나**, **`Dockerfile`로 직접 빌드**해서 얻는다.

| 구분 | 이미지 | 컨테이너 |
|------|--------|----------|
| 역할 | 코드와 설정을 담은 템플릿 | 이미지의 실행 인스턴스 |
