# 이미지 레이어와 빌드 캐시

> 도커 이미지는 **레이어 기반**이다. `Dockerfile`의 각 명령이 하나의 레이어가 되고, 결과는 **캐시**된다. 이 구조를 이해하면 빌드를 훨씬 빠르게 최적화할 수 있다.

## 레이어란?

- `Dockerfile`의 **명령 하나하나가 이미지의 레이어**를 나타낸다.
- 이미지는 여러 명령의 결과가 **차곡차곡 쌓인 레이어 묶음**이다.
- 이미지는 **읽기 전용**이다. 빌드가 끝나면 잠기고, 코드를 바꾸려면 다시 빌드해 **새 이미지**를 만들어야 한다.

```
Dockerfile                                     이미지 레이어
─────────────────────────────────────────      ─────────────────────
FROM python:3.14.5-alpine                  ──▶ 레이어 1 (베이스 이미지)
WORKDIR /app                               ──▶ 레이어 2
COPY requirements.txt .                    ──▶ 레이어 3
RUN pip install -r requirements.txt        ──▶ 레이어 4
COPY main.py .                             ──▶ 레이어 5
CMD [...]                                  ──▶ (실행 정보)
```

> 정확히는 파일 시스템을 바꾸는 명령(`RUN`, `COPY`, `ADD`)이 실제 레이어를 만들고, `CMD`, `EXPOSE` 같은 명령은 이미지의 **메타데이터**만 기록한다.

## 빌드 캐시 (Using cache)

변경 없이 `docker build`를 다시 실행하면 **매우 빠르게** 끝난다. 빌드 출력에 `Using cache`(BuildKit에서는 `CACHED`)가 표시된다.

- 도커는 **모든 명령의 결과를 캐시**한다.
- 다시 빌드할 때 명령과 입력이 이전과 **동일하면**, 명령을 다시 실행하지 않고 **캐시된 레이어를 재사용**한다.
- 즉 도커가 "이 명령은 다시 실행할 필요가 없다"고 판단하는 것이다.

이것을 **레이어 기반 아키텍처**라고 한다.

## 레이어가 하나 바뀌면?

코드를 수정하면 빌드 시간이 더 오래 걸린다. 일부 레이어만 캐시를 쓰기 때문이다.

> **한 레이어가 변경되면, 그 레이어와 그 이후의 모든 레이어가 다시 빌드된다.**

```
FROM ...                      ✔ 캐시 사용
WORKDIR /app                  ✔ 캐시 사용
COPY requirements.txt .       ✔ 캐시 사용
RUN pip install ...           ✔ 캐시 사용
COPY main.py .                ✘ main.py 변경 → 여기부터 다시 실행
CMD [...]                     ✘ 이후 레이어도 다시 빌드
```

- 도커는 **다시 실행해야 하는 부분만** 빌드해서 이미지 생성 속도를 높인다.
- 변경된 명령 **앞**의 레이어는 캐시를 쓰고, **그 명령부터 뒤**는 모두 다시 실행된다.

## 컨테이너를 실행하면?

이미지를 기반으로 컨테이너를 실행하면, 이미지 레이어 **위에 컨테이너 전용 레이어가 하나 더** 얹힌다.

```
┌────────────────────────────┐
│ 컨테이너 레이어 (쓰기 가능)   │  ← 컨테이너를 실행할 때만 생김
├────────────────────────────┤
│ 이미지 레이어 5 (읽기 전용)   │
│ 이미지 레이어 4 (읽기 전용)   │
│ 이미지 레이어 3 (읽기 전용)   │
│ ...                        │
└────────────────────────────┘
```

- `Dockerfile` 명령의 결과로 만들어진 레이어는 이미 **이미지의 일부**이며 각각 별도의 레이어다.
- 컨테이너 레이어는 실행 중 생기는 변경만 담는 **얇은 쓰기 가능 레이어**다. 이미지 레이어는 바뀌지 않는다.
- 이미지를 바꾸지 않으므로 같은 이미지로 **여러 컨테이너**를 실행해도 서로 영향이 없다.

## 빌드 최적화

### 문제: 코드를 바꿀 때마다 의존성을 다시 설치한다

아래처럼 모든 파일을 먼저 복사하면, **소스 코드가 바뀔 때마다** 그 뒤의 `pip install`(Node라면 `npm install`)이 다시 실행된다.

```dockerfile
FROM python:3.14.5-alpine
WORKDIR /app

COPY . .                                 # 코드가 바뀌면 여기서 캐시 무효화
RUN pip install -r requirements.txt      # → 매번 의존성을 다시 설치 ✘
```

의존성은 **의존성 파일이 바뀔 때만** 다시 설치하면 충분하다.

### 해결: 의존성 파일을 먼저 복사한다

의존성 파일만 먼저 복사해서 설치하고, 소스 코드는 **그 뒤에** 복사한다.

```dockerfile
FROM python:3.14.5-alpine
WORKDIR /app

COPY requirements.txt .                  # 의존성 파일만 먼저 복사
RUN pip install -r requirements.txt      # requirements.txt가 바뀔 때만 다시 실행 ✔

COPY main.py .                           # 소스 코드는 나중에 복사
```

- 소스 코드를 수정해도 **소스 복사 명령 앞의 레이어는 무효화되지 않는다.**
- 그래서 `pip install` 레이어는 캐시를 쓰고, 소스 복사 이후만 다시 빌드된다.
- 이 레포의 `Dockerfile`이 바로 이 구조다.

| 언어 | 의존성 파일 | 설치 명령 |
|------|-------------|-----------|
| Python | `requirements.txt` | `pip install -r requirements.txt` |
| Node.js | `package.json` | `npm install` |

> **원칙**: 자주 바뀌는 것(소스 코드)은 **뒤에**, 잘 안 바뀌는 것(의존성)은 **앞에** 둔다.

## 정리

| 개념 | 설명 |
|------|------|
| 레이어 | `Dockerfile` 명령의 결과. 이미지는 레이어의 묶음이다. |
| 캐시 | 명령과 입력이 같으면 이전 빌드 결과를 재사용한다. |
| 무효화 | 한 레이어가 바뀌면 그 이후 레이어는 모두 다시 빌드된다. |
| 컨테이너 레이어 | 컨테이너 실행 시 이미지 위에 얹히는 쓰기 가능 레이어. |
| 최적화 | 의존성 파일을 먼저 복사해 설치하고, 소스 코드는 나중에 복사한다. |
