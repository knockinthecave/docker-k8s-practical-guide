# 유틸리티 컨테이너 (Utility Containers)

## 1. 유틸리티 컨테이너란?

**특정 환경(예: Node + npm)만 갖추고 있고, 평소에는 아무것도 실행하지 않다가 내가 지정한 명령을 실행하기 위해 쓰는 컨테이너**이다.

- 앱을 "서비스"로 띄우는 컨테이너(웹서버, DB 등)와 달리, **개발 도구를 호스트에 설치하지 않고 쓰기 위한 컨테이너**이다.
- 예: `npm init`으로 `package.json`을 만들고 싶은데 호스트에 Node/npm을 설치하고 싶지 않을 때.
- Node뿐 아니라 PHP/Laravel(Composer, PHP 런타임 등)처럼 **호스트에 설치해야 할 도구가 많고 설정이 복잡한 언어**일수록 효과가 크다.

> 핵심 아이디어: **호스트에 도구를 설치하지 않고도, 호스트의 프로젝트 폴더에 결과물을 만들어 낼 수 있다.**

---

## 2. 실행 중인 컨테이너에 명령 내리기 — `docker exec`

이미 **실행 중인** 컨테이너 안에서, 그 컨테이너의 메인 명령(Dockerfile의 `CMD` 등)과 별개로 다른 명령을 실행한다.

```bash
docker exec -it CONTAINER_NAME npm init
```

| 옵션 | 의미 |
|------|------|
| `-i` | 표준 입력 유지 (프롬프트에 입력 가능) |
| `-t` | 터미널(TTY) 할당 |

- `-it`를 붙여야 `npm init`의 질문(패키지 이름, 버전 등)에 답할 수 있다.
- 호스트에 `node`/`npm`이 없어도 컨테이너 안의 것을 쓰므로 실행된다.
- 메인 프로세스를 멈추지 않고 컨테이너 내부 로그 파일 등을 확인할 때도 유용하다.

> ⚠️ `docker exec`는 **컨테이너가 떠 있어야** 쓸 수 있다. 유틸리티 용도로는 아래 3장의 `docker run`이 더 자연스럽다.

---

## 3. 기본 명령 덮어쓰기 — `docker run` + 명령

`docker run`에서 **이미지 이름 뒤에 쓴 명령은 이미지의 기본 `CMD`를 덮어쓴다.**

```bash
docker run -it node npm init
```

- `node` 이미지의 기본 명령(Node REPL) 대신 `npm init`이 실행된다.
- 같은 방식으로 프로젝트 설정 프롬프트가 뜬다.

### 문제: 컨테이너 안에서 만든 파일이 호스트에 없다

위 방식은 `package.json`이 **컨테이너 파일시스템 안에만** 생긴다. 호스트에서 쓰려면 **바인드 마운트**가 필요하다.

---

## 4. 바인드 마운트로 호스트 폴더와 공유하기

```bash
docker run -it -v $(pwd):/app 이미지이름 npm init
```

- `-v 호스트경로:컨테이너경로` — 호스트 폴더를 컨테이너 폴더와 **공유**한다.
- 컨테이너 안에서 `/app`에 만든 파일이 호스트의 현재 폴더에도 생긴다. → 유틸리티 컨테이너의 핵심 동작.

### 유틸리티 컨테이너용 Dockerfile

유틸리티 컨테이너를 만들려면 **자체 이미지**가 필요하다.

```dockerfile
FROM node:20-slim
WORKDIR /app
```

```bash
docker build -t node-util .
docker run -it --rm -v $(pwd):/app node-util npm init
```

- `--rm` : 명령이 끝나면 컨테이너를 자동 삭제 (일회성 작업이므로).

---

## 5. `ENTRYPOINT`로 명령 줄이기

`docker run ... node-util npm init`에서 매번 `npm`을 쓰는 게 번거롭다. `ENTRYPOINT`를 쓰면 줄일 수 있다.

```dockerfile
FROM node:20-slim
WORKDIR /app
ENTRYPOINT ["npm"]
```

```bash
docker run -it --rm -v $(pwd):/app node-util init
docker run -it --rm -v $(pwd):/app node-util install express
```

### `CMD` vs `ENTRYPOINT`

| | `CMD` | `ENTRYPOINT` |
|---|-------|--------------|
| `docker run 이미지 <명령>` 의 `<명령>` | **통째로 덮어씀** | **뒤에 인자로 붙음** |
| 예시 | `node-util npm init` → `npm init` 실행 | `node-util init` → `npm init` 실행 |

- `ENTRYPOINT ["npm"]`이면 이미지 이름 뒤에 쓴 `init`, `install express` 등이 모두 `npm` 뒤에 붙는다.
- 결과적으로 **이 이미지는 "npm 전용 실행기"** 가 되어 모든 npm 명령을 쓸 수 있다.

### 남은 단점

`docker run -it --rm -v $(pwd):/app node-util install express` — **명령이 너무 길다.** → Docker Compose로 해결.

---

## 6. Docker Compose로 짧게 쓰기

```yaml
services:
  npm:
    build: ./
    stdin_open: true   # docker run -i
    tty: true          # docker run -t
    volumes:
      - ./:/app        # 바인드 마운트
```

- `build: ./` — 같은 폴더의 Dockerfile(위의 `ENTRYPOINT ["npm"]` 버전)로 이미지를 빌드한다.
- `stdin_open` + `tty` — `-it`에 해당. 프롬프트 입력이 필요한 `npm init`에 필요하다.
- `volumes` — `-v $(pwd):/app`에 해당. 긴 마운트 옵션을 파일에 한 번만 써 두면 된다.

### 6.1 `up`이 아니라 `run`을 쓴다

| 명령 | 결과 |
|------|------|
| `docker compose up` | 서비스를 **띄우는** 명령. 유틸리티 용도에는 맞지 않음 (`ENTRYPOINT ["npm"]`만 실행되고 인자가 없음) |
| `docker compose up init` | ❌ 오류. `up` 뒤에는 **서비스 이름**이 와야 하는데 `init`은 서비스가 아님 |
| `docker compose run npm init` | ✅ `npm` 서비스를 실행하되, `init`을 **그 서비스에 넘기는 인자**로 사용 |

```bash
docker compose run npm init
docker compose run npm install express
```

- `docker compose run 서비스이름 인자...` — 여러 서비스가 정의돼 있어도 **단일 서비스만** 골라 실행할 수 있다.
- 서비스 이름(`npm`)이 `ENTRYPOINT`에 해당하고, 뒤의 `init`이 그 인자가 된다.

### 6.2 컨테이너 정리 — `--rm`

- `docker compose down`은 `up`으로 띄운 서비스를 정리한다. `run`으로 만든 컨테이너는 **`down`과 무관하게 남아 있을 수 있다.**
- `docker compose run --rm npm init` — 명령이 끝나면 **컨테이너를 자동 삭제**한다.

```bash
docker compose run --rm npm init
```

> `docker run`의 `--rm`과 같은 역할이다.

## 7. 명령 한눈에 비교

| 방식 | 명령 |
|------|------|
| 실행 중인 컨테이너에서 | `docker exec -it NAME npm init` |
| 기본 명령 덮어쓰기 | `docker run -it node npm init` |
| 바인드 마운트 + 자체 이미지 | `docker run -it --rm -v $(pwd):/app node-util npm init` |
| + `ENTRYPOINT ["npm"]` | `docker run -it --rm -v $(pwd):/app node-util init` |
| + Docker Compose | `docker compose run --rm npm init` |

## 8. Linux에서의 파일 권한 문제 ⚠️

> 강의 Q&A 스레드(Utility Containers and Linux)의 내용을 정리한 것이다. 강사(Maximilian)도 이 내용을 유틸리티 컨테이너 섹션에 반영하겠다고 답변했다.

### 문제

Docker는 기본적으로 컨테이너를 **root 사용자**로 실행한다. Linux에서 바인드 마운트한 폴더에 컨테이너가 파일을 만들면 **소유자가 root**가 된다.

```text
-rw-r--r-- 1 root root 202 Oct 31 16:16 package.json    ← 내 계정이 아닌 root 소유
```

- `npm init`뿐 아니라 `npm install`로 생기는 `node_modules` 등 **모든 산출물**이 root 소유가 된다.
- 호스트에서 수정/삭제하려면 `sudo`가 필요해진다.
- **macOS/Windows(Docker Desktop)** 는 VM을 거치며 사용자 매핑이 자동 처리되므로 보통 이 문제가 없다.

### 해결 1 — 이미지에 내장된 `node` 사용자 사용 (UID가 1000일 때)

공식 Node 이미지에는 UID/GID `1000:1000`인 `node` 사용자가 미리 만들어져 있다. 내 호스트 계정도 `1000:1000`이면 `USER node`만 추가하면 된다.

```dockerfile
FROM node:20-slim
USER node
WORKDIR /app
ENTRYPOINT ["npm"]
```

- 호스트 UID는 `id -u`, `id -g`로 확인한다.
- 이후 생성되는 파일의 소유자가 내 계정이 된다.

### 해결 2 — 내 UID/GID로 사용자를 새로 만들기 (UID가 1000이 아닐 때)

빌드 인자(`ARG`)로 호스트의 UID/GID를 받아 같은 번호의 사용자를 만든다.

```dockerfile
FROM node:20-slim

RUN userdel -r node

ARG USER_ID
ARG GROUP_ID

RUN addgroup --gid $GROUP_ID user
RUN adduser --disabled-password --gecos '' --uid $USER_ID --gid $GROUP_ID user

USER user
WORKDIR /app
ENTRYPOINT ["npm"]
```

```bash
docker build -t node-util:cliuser \
  --build-arg USER_ID=$(id -u) \
  --build-arg GROUP_ID=$(id -g) .

docker run -it --rm -v $(pwd):/app node-util:cliuser init
```

- `userdel -r node` — 기본 `node` 사용자(1000)와 UID가 충돌하지 않도록 제거.
- 이 이미지는 **빌드한 사람의 UID에 묶이므로 다른 환경에서는 이식성이 없다.** 개인 개발용 유틸리티 컨테이너에서는 큰 문제가 아니다.
- 참고: <https://vsupalov.com/docker-shared-permissions/>

### 요약

| 방법 | 조건 | 비고 |
|------|------|------|
| `USER node` | 호스트 UID/GID = 1000 | 가장 간단 |
| `ARG`로 사용자 재생성 | UID 무관 | 이미지가 빌드한 사람 전용 |

## 9. 정리

- 유틸리티 컨테이너 = **도구 환경만 담은 컨테이너 + 바인드 마운트**로, 호스트에 도구를 설치하지 않고 호스트 폴더에 결과물을 만든다.
- `docker exec`는 실행 중인 컨테이너에, `docker run <이미지> <명령>`은 기본 `CMD`를 덮어쓰는 방식으로 쓴다.
- `ENTRYPOINT ["npm"]`으로 `init`, `install ...`처럼 짧게 쓸 수 있다.
- 긴 `docker run` 옵션은 **Docker Compose**(`stdin_open`, `tty`, `volumes`)로 줄이고, **`docker compose run --rm 서비스 명령`** 으로 실행한다.
- Linux에서는 **root 소유 파일 문제**가 있으므로 `USER`를 지정한다.
