# 볼륨(Volume) 이해하기

> [02.Hands-on Data Types](./02.Hands-on%20Data%20Types.md)에서 확인한 것처럼 컨테이너 레이어의 데이터는 컨테이너를 삭제하면 사라진다. 이를 해결하는 것이 **볼륨**이다.

## 볼륨이란

- 볼륨은 컨테이너나 이미지 안에 있는 것이 아니라 **호스트 머신(내 컴퓨터)에 있는 폴더**다.
- 컨테이너 내부의 폴더가 이 호스트 폴더와 **연결(매핑)** 된다.
- 한쪽에서 변경하면 다른 쪽에도 반영된다. 컨테이너 외부에서도 데이터를 사용할 수 있다.

### `COPY`와의 차이

| | 동작 |
|---|------|
| `COPY` | 빌드 시점의 **일회성 스냅샷**. 이후 변경은 이어지지 않는다. |
| 볼륨 | 컨테이너 폴더와 호스트 폴더가 **계속 연결**된다. |

### 데이터 지속성

- 컨테이너가 종료되어도 볼륨은 계속 존재한다.
- 컨테이너를 삭제(`docker rm`)해도 볼륨의 데이터는 유지된다. (`--rm`으로 띄운 경우의 익명 볼륨은 예외, 아래 참고)
- 컨테이너는 볼륨의 데이터를 읽고 쓸 수 있다.
- 따라서 **컨테이너 삭제 후에도 살아남아야 하는 데이터**나 **외부에서 접근해야 하는 데이터**에 쓴다.

## 볼륨의 종류

도커의 외부 데이터 저장 방식은 크게 세 가지다.

| 종류 | 선언 방법 | 호스트 경로 | 특징 |
|------|-----------|-------------|------|
| **익명 볼륨** | Dockerfile의 `VOLUME` 또는 `-v /app/data` | 도커가 관리 (알 수 없음) | 이름이 없어 해시 이름이 붙는다. |
| **네임드(명명된) 볼륨** | `-v users-data:/app/data` | 도커가 관리 (알 수 없음) | 컨테이너를 삭제해도 남는다. 여러 컨테이너가 공유할 수 있다. |
| **바인드 마운트** | `-v /Users/me/data:/app/data` | **내가 직접 지정** | 호스트의 특정 폴더를 그대로 연결한다. |

익명 볼륨과 네임드 볼륨은 둘 다 도커가 호스트 어딘가에 폴더를 만들어 관리한다. 컨테이너 쪽 경로만 지정하고 호스트 쪽 경로는 지정하지 않기 때문에, **미러링된 폴더가 어디 있는지 우리는 모른다.** 이 폴더를 직접 열어 편집하는 용도가 아니며, 컨테이너가 사라질 때 같이 지워지지만 않으면 된다.

## 익명 볼륨

Dockerfile에 `VOLUME`을 쓰면 익명 볼륨이 된다.

```dockerfile
VOLUME ["/app/data"]
```

- 컨테이너 내부 경로만 지정했으므로 이름이 없다. `docker volume ls`에서 **64자리 해시 이름**으로 보인다.
- 볼륨 접근은 `docker volume` 명령으로만 가능하다.

```bash
docker volume ls
```

### 익명 볼륨이 삭제되는 조건

| 실행 방식 | 컨테이너 삭제 시 |
|-----------|------------------|
| `docker run --rm ...` | 컨테이너와 함께 익명 볼륨도 **자동 삭제** |
| `--rm` 없이 실행 후 `docker rm` | 익명 볼륨은 **남아 있음** |

다만 남아 있어도 도움이 되지 않는다. 같은 이미지로 다시 `docker run`하면 **새 익명 볼륨**이 만들어져 연결되므로, 이전 볼륨의 데이터를 이어서 쓸 수 없다. 결국 쓰이지 않는 볼륨만 쌓인다.

```bash
docker volume rm <VOL_NAME>   # 특정 볼륨 삭제
docker volume prune           # 사용하지 않는 볼륨 일괄 삭제
```

### `VOLUME` 사용 시 주의

- `VOLUME`은 "이 경로를 볼륨으로 쓴다"는 **선언**일 뿐, 도커가 파일을 다른 폴더로 옮겨 주지 않는다. 볼륨에 기대한 파일이 들어있는지 직접 확인해야 한다.
- 이미지에 `COPY`한 파일을 볼륨 경로에서 쓰려 해도 기대대로 동작하지 않을 수 있다. 데이터는 이미지가 아닌 볼륨 쪽에 있어야 한다.

## 네임드 볼륨

- Dockerfile 안에서는 만들 수 없고, **컨테이너를 실행할 때** `-v` 옵션으로 붙인다.
- 컨테이너 내부 경로 앞에 **이름**을 붙인다.

```bash
docker run -d -p 8000:8000 --name docker-practice-app -v users-data:/app/data docker-practice-image
```

- 컨테이너를 삭제해도 볼륨은 남아 있다. 같은 이름으로 다시 연결하면 데이터가 이어진다.
- 하나의 컨테이너에만 묶이지 않는다. 여러 컨테이너가 같은 볼륨을 공유할 수 있다.
- 도커가 관리하는 어딘가에 저장되며, 우리가 직접 편집할 필요가 없는 영구 데이터에 적합하다.

## 한눈에 비교

| | 익명 볼륨 | 네임드 볼륨 |
|---|-----------|-------------|
| 선언 | Dockerfile `VOLUME` / `-v /경로` | `docker run -v 이름:/경로` |
| 이름 | 자동 생성 해시 | 직접 지정 |
| 컨테이너 삭제 후 | `--rm`이면 삭제, 아니면 남지만 재사용 어려움 | **유지**, 이름으로 재연결 |
| 용도 | 임시로 컨테이너 밖에 빼 두는 데이터 | 컨테이너 삭제 후에도 살아남아야 하는 데이터 |

## 바인드 마운트

### 왜 필요한가

- 소스코드를 바꿔도 **이미지를 다시 빌드하지 않으면** 실행 중인 컨테이너에는 반영되지 않는다. (`COPY`는 스냅샷이므로)
- 개발 중에는 변경이 바로 반영되는 것이 중요하다. 매번 이미지를 빌드하고 컨테이너를 재시작하는 것은 번거롭다.
- 바인드 마운트는 소스 폴더를 컨테이너에 **연결**하므로 컨테이너가 항상 최신 코드를 본다.

### 네임드 볼륨과의 차이

| | 네임드 볼륨 | 바인드 마운트 |
|---|-------------|---------------|
| 호스트 경로 | 도커가 관리 (모름) | **내가 지정 (앎)** |
| 직접 편집 | 사실상 불가 | **가능** |
| 적합한 데이터 | 편집할 필요 없는 영구 데이터 | 영구적이면서 **편집 가능**한 데이터 (소스코드 등) |

### 사용법

컨테이너를 실행할 때 `-v 호스트 절대경로:컨테이너경로`로 붙인다. 폴더뿐 아니라 파일 하나만도 바인딩할 수 있다. 볼륨과 함께 여러 개의 `-v`를 쓸 수 있다.

```bash
docker run -d -p 8000:8000 --name docker-practice-app \
  -v users-data:/app/data \
  -v /Users/me/project:/app \
  docker-practice-image
```

- 공유할 폴더에 **도커가 접근할 권한**이 있어야 한다. (Docker Desktop은 파일 공유 설정, 리눅스는 폴더 접근 권한 관리)

### 주의: 컨테이너 내부 파일이 덮어써진다

이미지를 만들 때 소스를 `/app`에 복사하고 의존성도 설치해 두었다고 하자. 호스트 폴더를 `/app`에 바인드 마운트하면 **호스트 폴더의 내용이 컨테이너의 `/app`을 덮어쓴다.**

- 도커가 호스트 파일을 덮어쓰는 것이 아니다. 방향은 항상 **호스트 → 컨테이너**다.
- 호스트 폴더에는 `npm install` 같은 의존성 설치 결과가 없으므로, 이미지 빌드 때 설치한 것이 가려져 **빌드 과정이 무의미**해진다.

### 해결: 덮어쓰지 않을 경로에 익명 볼륨 추가

덮어쓰이면 안 되는 하위 경로(예: `node_modules`)를 익명 볼륨으로 따로 지정한다.

```bash
docker run -v /Users/me/project:/app -v /app/node_modules ...
```

- 도커는 컨테이너에 설정한 모든 볼륨을 평가하고, 경로가 충돌하면 **더 길고 구체적인 내부 경로를 우선**한다.
- `/app`(바인드 마운트)과 `/app/node_modules`(익명 볼륨)가 있으면 `/app/node_modules`는 바인드 마운트에 덮어써지지 않는다.
- 따라서 이미지 빌드 중 `npm install`로 만들어진 `node_modules`가 그대로 살아남는다.

이렇게 하면 이미지를 다시 빌드하지 않아도 코드 변경이 바로 컨테이너에 적용된다.

> 이 프로젝트(FastAPI)는 의존성이 `/app`이 아닌 파이썬 `site-packages`에 설치되므로 이 충돌이 생기지 않는다. 위 예시는 `node_modules`가 `/app` 아래에 생기는 Node.js 기준이다.

## 요약

### 익명 볼륨

- 컨테이너에 연결되는 볼륨을 생성한다. 호스트 머신에 폴더가 만들어지긴 하지만 경로는 도커가 관리한다.
- `--rm`으로 실행한 컨테이너가 제거되면 익명 볼륨도 함께 사라진다.
- 컨테이너에 종속되므로 **컨테이너 간 데이터 공유에는 쓸 수 없다.**
- 대신 컨테이너에 **이미 존재하는 특정 데이터를 보호(덮어쓰기 방지)** 하는 데 유용하다. (예: 바인드 마운트 아래의 `node_modules`)
- 시간 절약에도 도움이 된다.

### 네임드 볼륨

- 이름을 지정해 만들며 `docker run -v 이름:/경로`로 붙인다. Dockerfile에서는 만들 수 없다.
- 컨테이너를 삭제해도 남고, 여러 컨테이너가 공유할 수 있다.
- 직접 편집할 필요 없는 **영구 데이터**용이다.

### 바인드 마운트

- 호스트의 특정 경로를 내가 지정해 컨테이너에 연결한다.
- 직접 편집이 가능해 **개발 중 소스코드 실시간 반영**에 쓴다. (이미지 재빌드 불필요)
- 호스트 내용이 컨테이너 경로를 덮어쓰므로, 지켜야 할 하위 경로는 익명 볼륨으로 지정한다.

| | 익명 볼륨 | 네임드 볼륨 | 바인드 마운트 |
|---|-----------|-------------|---------------|
| 호스트 경로 | 도커 관리 | 도커 관리 | **직접 지정** |
| 컨테이너 삭제 후 | `--rm`이면 삭제 | 유지 | 유지 (호스트 폴더이므로) |
| 컨테이너 간 공유 | 불가 | 가능 | 가능 |
| 직접 편집 | 불가 | 사실상 불가 | **가능** |
| 주 용도 | 특정 경로 보호 | 영구 데이터 | 개발 중 코드 반영 |
